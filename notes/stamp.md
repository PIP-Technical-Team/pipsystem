## S1. Can a partition be a parent?

**Answer: yes through the ordinary artifact path; selective invalidation is not directly tested.** `st_save_part()` makes a path with `st_part_path()` and calls `st_save()` with code and parents (`R/partitions.R:175-212`). The normal save records content/code hashes, a catalog artifact row, a version row, parent index rows, and a snapshot (`R/IO_core.R:310-382`; `R/version_store.R:682-729,750-829`). A parent descriptor is a path and version ID; there is no whole-dataset restriction. Thus a concrete partition path/version can be passed as a parent. Staleness compares that recorded parent version with the latest version of that path (`R/version_store.R:1203-1217`). This is source-path support, not a proved partition-parent round trip.

Auto-partition support at this SHA is named `st_write_parts()`, not `st_auto_partition()`. It splits input data and calls `st_save_part()` separately for each part, then returns a path/version manifest (`R/partitions.R:266-317,342-428`; `NAMESPACE:30-46`). It does not create a versioned aggregate dataset or a separate automatic partition-state registry in this path. Its `parents` argument is copied to each output partition; it does not discover which parent rows each output uses (`R/partitions.R:362-374`). Partition auto-save state and declared parent lineage are different things.

A skipped `st_save()` has no `version_id`; `st_save_part()` returns that missing value, and `st_write_parts()` substitutes NA. Callers must not treat an unchanged manifest entry as a new version or a valid newly returned parent pin (`R/IO_core.R:259-269`; `R/partitions.R:211,384-389`). Removed input keys are not deleted or invalidated by the auto-save loop (`R/partitions.R:342-428`). Parent structure normalization keeps path/version fields but does not canonicalize their paths. For reliable parent IDs, callers need the absolute logical artifact path, not a relative path resolved from an unrelated working directory (`R/version_store.R:22-24,799-813,909-943`).

## S2. What goes into code_hash?

**Answer: function, expression/language, or character label in source.** Functions hash deparsed formals and body, not their environment or transitive called functions. The `is.language()` branch deparses its input; other inputs use `as.character()` joined with newlines. Spaces/tabs and CR line endings are normalized, then SipHash-1-3 is applied (`R/hashing.R:318-342`). A caller can use `code = "deflate-v2"` as an explicit version label; the label is still hashed. `code_label` is only stored text, not the code-hash input (`R/IO_core.R:318-334`). Exact expression-vector hash behavior is not tested in the inspected tests (`R/hashing.R:327-333`).

If `code = NULL` or the `code_hash` option is disabled, saved `code_hash` is NA (`R/IO_core.R:318-324`). With no current code, or hashing disabled, `st_changed()` reports `code_changed = NA` and `isTRUE()` ignores that component. With code supplied and hashing enabled, an old NA is compared with a newly computed hash and counts as a code change (`R/hashing.R:500-529`). `st_is_stale()` does not compare code hashes at all; it only compares immediate parent version IDs (`R/version_store.R:1176-1217`). NA therefore does not mean stale by itself and does not provide automatic code-change detection.

**TEST evidence, inspected, not run:** `tests/testthat/test-should-save.R:1-34` checks unchanged function code and changed function code in save decisions. `tests/testthat/test-catalog-query.R:103-112` checks the code_hash column, not code-label or NA semantics. Direct explicit-version-label, expression, function-environment and NA-transition tests are UNKNOWN.

The option `force_on_code_change` exists in defaults/validation, but the save decision above does not read it. Code differences count in mode `any` regardless of that option (`R/aaa.R:183-195`; `R/options.R:55-62`; `R/IO_core.R:974-995`; `R/hashing.R:500-529`). This is not an alternative to supplying an explicit label.

## S3. Early cutoff

**Answer: partial.** Under the default content policy, identical object content with unchanged or omitted code and no detected file change is skipped before writing a sidecar, catalog row or snapshot. No new version is created (`R/aaa.R:183-195`; `R/IO_core.R:253-269,952-995`; `R/hashing.R:492-529`). A direct child whose recorded parent pin was current stays current because the parent version did not advance (`R/version_store.R:1208-1217`). This is version-based cutoff, not a recursive rebuild-engine cutoff.

Identical content alone is insufficient. A code change still saves a new version; `versioning = "timestamp"` also saves unchanged content, and a detected file change can trigger a save (`R/IO_core.R:974-995`; `R/hashing.R:500-539`). The catalog version ID includes timestamp and code hash as well as artifact/content hash (`R/version_store.R:761-770`). Children compare version IDs, not content hashes, so they can become stale when content is identical but a new version is made (`R/version_store.R:1208-1217`).

There is an integration limit. Suppose A advances, B is rebuilt from A, but B's output and code stay identical. `parents` is not part of the save decision, so B's save can skip and leave B pinned to old A. B remains stale, while C pinned to unchanged B does not become directly stale (`R/IO_core.R:253-269,952-995`; `R/version_store.R:1203-1217`). `st_rebuild()` treats the skipped save as `failed`, because it has no returned version ID; it does not report `unchanged` or update the parent pin. Any later rows already in the plan still execute; the executor does not recheck their staleness or prune their cascade after identical output (`R/rebuild.R:214-241,296-342`).

**TEST evidence, inspected, not run:** `tests/testthat/test-should-save.R:83-115` asserts one version after an identical save, then two after changed content. `:16-34,63-81` covers code change and timestamp/off decisions. No inspected automated test covers the A-to-B identical-output lineage refresh or executor cutoff. The manual chain script asserts direct rather than transitive staleness (`tests/manual/test_stamp_smoke.R:259-268`), but is not an executed result.

## S4. Scale and concurrency

**Answer: centralized whole-catalog IO with best-effort locks; target scale and parallel safety are UNKNOWN.** Initialization creates `<root>/.stamp/`, `temp/`, and `logs/` by default (`R/IO_core.R:16-20,94-105`). State contains `catalog.qs2`, with artifact, version and parent-index tables. `catalog.lock` is used on catalog updates (`R/version_store.R:109-146,772-827`). Current artifact data, sidecars and version snapshots are outside `.stamp`, under each artifact directory. For a logical `dir/file.fst`, the data file is `<root>/dir/file.fst/file.fst`, sidecars are under `stmeta/`, and snapshots are `versions/<version_id>/artifact`, `sidecar.json|qs2`, and optional `parents.json` (`R/utils.R:45-82`; `R/format_registry.R:242-251`; `R/version_store.R:88-98,631-661,853-874`). The old centralized `.stamp/versions` helper is deprecated, not the current save layout (`R/version_store.R:60-76`).

`st_catalog_query()` reads the entire QS2 catalog, then joins all artifact latest-version IDs to the version table and returns six fields per artifact. It does not scan each artifact sidecar for this query (`R/version_store.R:156-171,1257-1311`). Cost and memory therefore grow with the stored catalog, including historical versions and parent-index rows, not only the number of result rows. Saves append version/parent rows and rewrite the whole catalog; the catalog lock serializes that part (`R/version_store.R:726-729,775-827,183-192`). Exact complexity, throughput and memory at tens of thousands of artifacts are UNKNOWN. Small catalog tests cover three artifacts, latest-version selection, schemas and invalid aliases, not this scale (`tests/testthat/test-catalog-query.R:13-37,41-99,161-163`).

Concurrency paths found in source:

- Artifact write, sidecar, catalog record and snapshot copy run under an artifact lock; the catalog read/modify/write also takes `catalog.lock` (`R/IO_core.R:275-393`; `R/version_store.R:772-827`). Locks are real only if optional `filelock` is installed. Otherwise the helper runs the expression without exclusion (`R/IO_core.R:1027-1044`).
- The helper calls `filelock::lock(..., timeout = 5000)` but does not check that a lock was acquired before evaluating the expression. Lock-timeout behavior and mutual exclusion in that path are not tested here (`R/IO_core.R:1036-1042`).
- Save/no-save decisions happen before the artifact lock, and are not repeated under it. Two writers can both decide to save the same input before either writer commits; the later writer can create another version or replace current data even if content became identical (`R/IO_core.R:253-279`). With working locks, current data follow write order, not a compare-and-swap rule.
- Artifact, sidecar and catalog replacement delete the existing destination before moving the temporary file. Readers do not take these locks. A reader can see a missing destination in the delete/move interval; without exclusion, catalog writers can lose each other's updates or fail on conflicting deletion/moves (`R/IO_core.R:1014-1021`; `R/format_registry.R:284-302`; `R/version_store.R:156-158,183-192`). These are source-derived race paths, not reproduced corruption.
- Catalog recording precedes snapshot creation, so a reader can see a catalog version before its snapshot exists. Failure after the data or catalog write has no transaction rollback in `st_save()`; it warns and returns NULL metadata/version fields (`R/IO_core.R:347-408`). A global consistent multi-artifact read is not established by these locks.

**TEST evidence, inspected, not run:** `tests/testthat/test-edgecases.R:1-21` checks one lock helper call and five sequential saves, not parallel processes or timeout contention. `tests/testthat/test-save-load.R:115-136` checks no remaining temporary files after one save. `tests/testthat/test-edgecases.R:76-98` corrupts a catalog deliberately and repairs it by deleting it, not by concurrency. No multi-process, shared network-drive or tens-of-thousands-of-artifacts test was found in `tests/`. Their results remain UNKNOWN.

## S5. Builder API

**Answer: implemented bodies, but incomplete integration and weak test evidence.** `st_register_builder()` stores a function keyed by normalized path and name in an in-memory environment. It is not a persistent build-rule catalog (`R/rebuild.R:3-47`; `R/aaa.R:38-39`). `st_rebuild()` accepts a provided function or selects the first matching path in the registry; it has no builder-name selector or alias argument (`R/rebuild.R:161,191-209`).

`st_plan_rebuild()` accepts multiple target paths, depth, include-targets and propagate/strict modes. It returns level/path/reason/latest-version-before rows. Include-targets in propagate mode includes targets unconditionally, despite the nearby stale-only description (`R/rebuild.R:371-419`). It gets immediate children from recorded reverse lineage (`R/rebuild.R:138-146,424-429`). Reverse lineage includes relationships from historical child versions, not only each child's current parent set, so these are candidates that need current-lineage checks (`R/version_store.R:799-822,976-1012`).

Two modes have distinct limits:

- **Propagate:** targets are assumed to change, and candidate children with such parents are scheduled without a current version comparison (`R/rebuild.R:397-398,454-509`). However, it then computes the next frontier by removing all planned paths. In the simple chain A -> B -> C, B is scheduled, B is removed from the next frontier, and the loop breaks before visiting C. This is a direct source trace, not an executed result (`R/rebuild.R:495-518`).
- **Strict:** traverses candidates but includes only artifacts already stale against their immediate parents' current version IDs (`R/rebuild.R:434-451`; `R/version_store.R:1176-1217`). After A changes but B has not rebuilt, B is stale and C is not. It is not transitive invalidation. Strict traversal has no visited-frontier guard; cycles are not validated before depth-Inf traversal (`R/rebuild.R:421-451`).

The returned levels are traversal levels, not a full DAG topological sort. In propagate mode a multi-target input can include a dependent target at level zero alongside its parent; all targets are added at level zero without ordering by dependencies (`R/rebuild.R:400-419`). Reliable general DAG planning at target scale is UNKNOWN.

The executor sorts rows by level/path, refreshes declared parent pins to latest, supports dry run, calls a builder, requires a list with non-NULL `x`, forwards format/metadata/code/code_label to `st_save`, and returns `built`, `failed`, or `dry_run` rows (`R/rebuild.R:173-189,211-353`). Builder errors and missing builders become failures and work continues. But parent discovery occurs outside those error handlers; failures there can stop the call (`R/rebuild.R:227,248-276`). It does not block a dependent after a parent fails, does not recheck staleness between planned rows, and treats skipped saves as failed (`R/rebuild.R:253-342`). There is no persisted failed-artifact state in the catalog schema or staleness predicate (`R/version_store.R:122-146,1176-1217`). Missing artifacts/versions and missing parent versions are not consistently treated as stale by `st_is_stale()` (`R/version_store.R:1181-1217`), though `st_should_save()` does allow a first missing artifact write (`R/IO_core.R:959-969`).

## S6. Custom metadata

**Answer: supported in source, with test and update limits.** `st_save(metadata = list(...))` appends the supplied list to the built-in sidecar fields (`R/IO_core.R:193-207,310-348`). Thus distinct custom keys such as `module`, `module_version`, `data_type`, `dlw_master_version`, and `dlw_harmonization_version` can be supplied as extra fields. These names are proposed caller keys, not built-in stamp fields. No PIP field schema or validation is present in that merge. The merge is `c(list(...), metadata)`, not a checked override; avoid collisions with built-in keys (`R/IO_core.R:310-345`).

`st_read_sidecar(path, alias)` reads only JSON or QS2 sidecar content. It does not call an artifact reader. JSON has priority, uses `simplifyVector = TRUE`, and a missing sidecar returns NULL (`R/format_registry.R:319-347`). JSON writes use `auto_unbox = TRUE`, so JSON readback need not preserve all R list/vector types (`R/format_registry.R:267-302,339-345`). `st_info(path, alias)$sidecar` also exposes the sidecar without loading data, but reads the catalog and latest snapshot parents too (`R/IO_core.R:630-660`). Neither public reader has a version argument; these interfaces expose current sidecars, not a requested past version (`R/format_registry.R:319`; `R/IO_core.R:630-660`). Historical sidecars are copied into snapshots as `sidecar.json` and/or `sidecar.qs2`; a caller can read these files without loading snapshot data, but these readers do not supply that version-selection interface (`R/version_store.R:631-661`).

The physical sidecar is in `<artifact-storage-directory>/stmeta/<filename>.stmeta.json` or `.qs2`, not necessarily a flat adjacent file (`R/format_registry.R:242-251`). Tests assert `test.qs2/test.qs2`, `test.qs2/stmeta`, and `test.qs2/versions` (`tests/testthat/test-folder-structure.R:20-44`).

Important limit: save decisions use object and code, not `metadata` or `parents`. A no-change decision returns before the sidecar is written. A metadata-only change can therefore be skipped under the default content policy (`R/IO_core.R:253-269,952-995`). Custom metadata does not itself form an invalidation signal in this path.

**TEST evidence, inspected, not run:** `tests/testthat/test-pk.R:1-17` checks built-in PK sidecar readback; `tests/testthat/test-folder-structure.R:162-185` checks `st_info` fields; `tests/testthat/test-info-retention-children.R:1-21` checks counts and snapshot location. These are not direct tests of arbitrary custom metadata. A search for `metadata =` in `tests/` returned no matching custom-metadata fixture; an executed custom-field round trip is UNKNOWN.

## S7. Release scoping

**Answer: no native named release/set registry; caller-owned manifests are possible.** The catalog has only artifacts, versions and parent-index tables; aliases map a name to root/state paths, not to a frozen set of version pins (`R/version_store.R:122-146`; `R/aaa.R:32-36,61-77`). Exports include artifact version and catalog APIs, but no release/set create/load/freeze API (`NAMESPACE:3-46`). `st_catalog_query()` returns latest versions for all artifacts in one alias, which is a current-state view, not a named persistent snapshot with atomic multi-artifact capture (`R/version_store.R:1257-1311`). No release/set implementation was found by a source search for release; a dedicated named-release test is UNKNOWN.

A caller could store its own list/table of absolute artifact paths and version IDs as a normal, named artifact. This is possible because `st_save()` accepts generic objects and custom metadata; it would be caller-defined data, not built-in release semantics (`R/IO_core.R:193-207,247-258,310-348`). Artifact parent descriptors can also pin a list of path/version pairs (`R/version_store.R:799-822,853-874,909-943`). Such a manifest must supply its own membership checks, scope, publication/freeze state and retention protection; none is part of the inspected APIs. Default retention keeps all versions, but optional pruning can remove snapshots and catalog rows without a named-release reference model (`R/aaa.R:188-190`; `R/retention.R:415-435`).

Individual historical data retrieval does exist: `st_load(file, version = <ID>)` resolves a specific catalog version and calls `st_load_version()`, which reads the stored `artifact` snapshot (`R/IO_core.R:483-498`; `R/version_store.R:355-380,452-489`). That is not a guarantee that a named multi-artifact release remains available.

**TEST evidence, inspected, not run:** `tests/testthat/test-folder-structure.R:240-268` saves two versions and loads the first. `tests/testthat/test-catalog-query.R:69-99` verifies latest-only catalog rows; `tests/testthat/test-info-retention-children.R:23-47` selects prune candidates. None tests a named release, freeze state, concurrent capture or release-aware retention. Decided release links/reproducibility (`SYSTEM_DESIGN.md:26-28,236-244`) remain caller-layer requirements; they are not native stamp capabilities demonstrated here.
