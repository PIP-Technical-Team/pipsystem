# HARVEST_BRIEF.md

Specification for Phase 1 of `pipsystem`: extracting structured facts about how the PIP R
packages read data, write data, consume auxiliary data, and encode cleaning rules, and
about what `stamp` can and cannot already do for us.

This file defines **what to extract and in what schema**. It does not define how the work
is sequenced or verified. That belongs to the plan produced by `/cg-plan`.

Read `compound-gpid.md` first. The Objective and Constraints there govern everything
below.

## 1. Purpose

The goal is **not** README style prose. It is verifiable tables.

Everything produced here serves one end: building a system that detects what changed and
reruns only what is affected. When choosing what to record, favor facts that answer
"what does this depend on and what does it produce" over facts that answer "what does
this function do".

Packages: `stamp`, `pipfun`, `pipload`, `pipaux`, `pipdata`, `wbpip`, `pipapi`,
`pipster`, `pipfaker`, `metapip`.

`stamp` is different from the rest. It is a general purpose versioned artifact store
maintained by this team and intended for use outside PIP. It already implements much of
what `pipsystem` needs: content and code hashing, lineage, staleness, a catalog, and an
experimental rebuild planner. The reason to read it is not to inventory it but to
determine **which requirements it already meets, which it partially meets, and which are
absent**, with evidence.

## 2. Rules

Beyond the charter constraints:

1. **Tables are CSV.** No prose in cells beyond a short `notes` field. Longer
   observations go in the package note file.
2. **Every row carries a file and line reference.**
3. **`UNKNOWN` is a valid value. A plausible guess is not.**
4. **Gaps sections must never be empty.** An empty Gaps section is treated as evidence
   that the package was summarized rather than read, and that package's output is
   discarded and redone.
5. **Column names are fixed.** They must be identical across packages so the tables
   concatenate cleanly.
6. **Read the code, not the README.** For `stamp` especially, the README describes
   intent. Several features are marked experimental or under development. Only the source
   and the tests establish what actually works.

## 4. Mechanical extraction

Write `R/extract.R`. It must be deterministic, rerunnable, and free of any model
judgment. It produces `identity.csv`, `api.csv`, `deps_internal.csv`, and `config.csv`.

A starting skeleton is below. **Verify and fix it. Do not assume it runs.** In
particular, confirm how commit SHAs are available in this environment (packages installed
via `remotes` carry `RemoteSha`; local clones carry it in git) and confirm whether the
packages are installed, present as source clones, or both.

Note that `stamp` is not currently a dependency of the PIP packages, so it will produce
no rows in `deps_internal.csv`. That is expected, not a bug.

```r
# pipsystem/R/extract.R
# Mechanical harvest of the PIP package ecosystem.
# Requires: packages installed (for reflection) and source clones (for config grep).

library(data.table)

PKGS <- c("stamp", "pipfun", "pipload", "pipaux", "pipdata", "wbpip",
          "pipapi", "pipster", "pipfaker", "metapip")

SRC_ROOT <- "<workspace root holding the sibling clones>"

`%||%` <- function(a, b) if (is.null(a)) b else a

# ---- identity ---------------------------------------------------------------
get_identity <- function(p) {
  d <- packageDescription(p)
  data.table(
    package      = p,
    version      = d$Version,
    repo_url     = d$RemoteUrl %||% NA_character_,
    branch       = d$RemoteRef %||% NA_character_,
    commit_sha   = d$RemoteSha %||% NA_character_,
    imports      = d$Imports   %||% NA_character_,
    suggests     = d$Suggests  %||% NA_character_,
    remotes      = d$Remotes   %||% NA_character_,
    harvest_date = as.character(Sys.Date())
  )
}

# ---- api --------------------------------------------------------------------
get_api <- function(p) {
  ns <- asNamespace(p)
  rbindlist(lapply(getNamespaceExports(p), function(f) {
    obj <- get(f, envir = ns)
    data.table(
      package   = p,
      function_ = f,
      is_fun    = is.function(obj),
      signature = if (is.function(obj))
                    paste(deparse(args(obj)), collapse = " ") else NA_character_
    )
  }))
}

# ---- deps_internal ----------------------------------------------------------
# Edges between the packages above only.
build_export_map <- function(pkgs) {
  rbindlist(lapply(pkgs, function(p)
    data.table(callee_package = p, callee_function = getNamespaceExports(p))))
}

get_deps <- function(p, export_map) {
  ns  <- asNamespace(p)
  fns <- ls(ns, all.names = TRUE)
  edges <- rbindlist(lapply(fns, function(f) {
    obj <- tryCatch(get(f, envir = ns), error = function(e) NULL)
    if (!is.function(obj)) return(NULL)
    g <- tryCatch(codetools::findGlobals(obj, merge = FALSE)$functions,
                  error = function(e) character(0))
    if (!length(g)) return(NULL)
    data.table(caller_package = p, caller_function = f, callee_function = g)
  }), fill = TRUE)
  if (!nrow(edges)) return(NULL)
  merge(edges, export_map, by = "callee_function")[caller_package != callee_package]
}

# ---- config -----------------------------------------------------------------
# Source level grep over the clones.
CONFIG_PATTERNS <- c(
  option  = "getOption\\s*\\(|options\\s*\\(",
  env_var = "Sys\\.getenv\\s*\\(|Sys\\.setenv\\s*\\("
  # ADD any pipfun specific config accessor once identified
)

get_config <- function(p) {
  dir <- file.path(SRC_ROOT, p, "R")
  if (!dir.exists(dir)) return(NULL)
  rbindlist(lapply(list.files(dir, pattern = "\\.[Rr]$", full.names = TRUE), function(fp) {
    lines <- readLines(fp, warn = FALSE)
    rbindlist(lapply(names(CONFIG_PATTERNS), function(kind) {
      hits <- grep(CONFIG_PATTERNS[[kind]], lines)
      if (!length(hits)) return(NULL)
      data.table(package = p, kind = kind, file = basename(fp),
                 line = hits, raw = trimws(lines[hits]))
    }))
  }), fill = TRUE)
}
```

Run it, inspect the output, report row counts per table. If `deps_internal.csv` is empty
or implausibly small for the PIP packages, the namespaces are probably not all loaded.
Fix that before going further; every later step assumes this table is real.

## 5. `stamp`: capability assessment

**Read `stamp` first.** It establishes the vocabulary (artifact, version, parent,
content hash, code hash, staleness, partition) that the rest of the harvest maps onto.
The questions below are self contained and do not require knowing anything about PIP.

Produce `tables/stamp_fit.csv` and `notes/stamp.md`.

### 5.1 The five questions

Answer each explicitly in `notes/stamp.md`, in prose, with file and line evidence. These
determine whether the PIP pipeline fits on `stamp` as it stands.

**Q1. Can a partition be a parent?**
Partitions are Hive style and marked under development. Determine whether a partition
written by `st_save_part()` or `st_auto_partition()` is an addressable artifact in its own
right: does it get its own entry in the catalog, its own version, its own content hash,
and can another artifact declare it as a parent so that changing one partition marks only
the dependent artifacts stale? Or does lineage operate only at whole artifact level, so a
change to any partition invalidates every consumer of the whole dataset?

This is the single most important question in the harvest. A CPI table decomposed into
country year partitions, each independently addressable as a parent, is exactly the
mechanism the PIP pipeline needs.

**Q2. What exactly goes into `code_hash`?**
Trace `st_hash_code()` and the `code` argument of `st_save()`. Determine what can be
passed: a function, an expression, a character string, something else. If a whole function
body is hashed, any edit to that function changes the hash for every artifact it produced.
Determine whether an explicit version string can be supplied instead, so that code
versions are bumped deliberately rather than on every edit. Record whether `code_hash` is
optional, and what happens to staleness when it is `NA`, as it is in the README example.

**Q3. Does staleness propagate on `version_id` or on `content_hash`?**
Trace `st_is_stale()`, `st_changed()`, and `st_should_save()`. Determine what happens when
a rebuild produces byte identical content: is a new version created, and do children
become stale anyway, or does the cascade stop? A cascade that stops on identical content
is the difference between hours and minutes on fan in layers. If it does not stop, record
whether it could.

**Q4. How does the catalog behave at scale and under concurrency?**
Determine the physical structure of `.stamp/`: sidecars per artifact, a single index, or
both. Determine what `st_catalog_query()` reads and whether its cost grows linearly with
artifact count. Then determine what happens when many processes call `st_save()`
simultaneously: is there locking, is it last write wins, can the catalog be corrupted.
Target scale is tens of thousands of artifacts with parallel workers.

**Q5. How stable is the builder API?**
`st_register_builder()`, `st_plan_rebuild()`, `st_rebuild()`, and the filtering helpers
are flagged experimental. Determine their actual state from the source and tests: what
works, what is stubbed, what is tested. Report the test coverage of these functions
specifically, not of the package overall.

### 5.2 `stamp_fit.csv`

One row per requirement. Columns:

```
requirement, stamp_function, status, evidence_file, evidence_line, notes
```

* `status`: `supported`, `partial`, `absent`, `unknown`
* `stamp_function`: the function that provides it, or `NA` if absent
* `notes`: for `partial`, state precisely what is missing

Requirements to assess, at minimum:

| requirement |
|---|
| content addressed storage of an artifact |
| retrieval of a specific historical version |
| declaring an artifact's inputs (parents) |
| querying an artifact's dependents (children) |
| determining whether an artifact needs rebuilding |
| transitive staleness across more than one level |
| partition level addressing |
| partition as a declared parent |
| code version as an explicit string rather than a hashed function |
| early cutoff when rebuilt content is identical |
| recording which inputs were actually consumed at run time |
| bulk catalog query without per artifact iteration |
| concurrent writes from parallel workers |
| retention and pruning of old versions |
| planning a rebuild across many targets |
| executing a rebuild plan |
| scoping a whole catalog to a named release or snapshot |

Add rows for anything else `stamp` does that looks relevant. Do not remove rows that come
back `absent`; those are the design work.

### 5.3 `notes/stamp.md`

Same structure as the other package notes, plus a section answering the five questions.
Add an explicit section listing **what `stamp` would need to gain** for the PIP pipeline
to run on it, phrased as capability gaps rather than as proposed implementations.

Keep the domain boundary in view: `stamp` must stay free of PIP concepts. If a gap can
only be closed by teaching `stamp` about surveys or CPI, say so, because that means the
gap belongs in `pipsystem` instead.

## 7. Column schemas

Use these exact column names.

**io_points.csv**
```
package, function_, file, line, direction, target_kind, target,
path_source, config_key, format, notes
```
* `direction`: `read` or `write`
* `target_kind`: `file`, `blob`, `db`, `api`, `option`, `env`, `other`
* `path_source`: `hardcoded`, `constructed`, `config`, `argument`
* `format`: `fst`, `parquet`, `rds`, `dta`, `csv`, `qs`, `qs2`, `UNKNOWN`, and so on

**aux_access.csv**
```
package, function_, file, line, series, granularity, key_columns,
key_set, loads_full_table, notes
```
* `series`: `cpi`, `ppp`, `pop`, `gdp`, `pce`, `gdm`, `other`
* `granularity`: the level at which the lookup actually happens, one of
  `global_table`, `country`, `country_year`, `country_year_level`, `other`
* `key_columns`: the actual join or subset columns used
* `key_set`: `static` if the keys are known before running, `runtime` if the code decides
  at execution time which cells to pull
* `loads_full_table`: `TRUE` if the whole series is read into memory then subset,
  `FALSE` if only the required cells are requested

**outputs.csv**
```
package, function_, artifact_name, storage_location, format,
primary_key, columns, columns_source, notes
```
* `primary_key`: the columns that uniquely identify a row, if determinable
* `columns`: semicolon separated
* `columns_source`: `declared` if the code states the schema explicitly, `inferred` if
  derived from the transformations

**rules.csv**
```
package, rule_id, rule_name, rule_kind, defined_in, definition_location,
scope, has_overrides, override_location, on_failure, file, line, notes
```
* `rule_kind`: `cleaning`, `validation`, `imputation`, `exclusion`, `transformation`
* `defined_in`: `code` or `data`
* `definition_location`: path to the file or dataset holding the definition
* `scope`: `global`, `region`, `country`, `survey`, `welfare_type`
* `on_failure`: `drop`, `flag`, `error`, `impute`, `skip`, `UNKNOWN`

**notes/<package>.md**
```markdown
# <package> @ <commit sha>

## Purpose in one paragraph

## Side effects
Global state mutation, caching, memoization, anything written outside a return value.

## Execution order dependencies
What must run before what, and what breaks if it does not.

## Surprises
Anything contradicting the README, the vignettes, or what another package appears
to assume.

## Gaps
What could not be determined, with file and line. MUST NOT BE EMPTY.

## Open questions for the maintainer
```

## 8. Per package emphasis

**pipfun.** Is this genuinely the only owner of configuration and paths, or do other
packages construct paths themselves? Every config key with its default and its consumers.
Any global option that silently changes behavior.

**pipload.** Reconstruct the storage layout as a path grammar. How are vintages and
versions encoded in paths? How is the inventory built, and is it cached? What determines
whether a survey counts as available? Note explicitly where this overlaps with what
`stamp` already provides, since both manage versioned artifacts on disk.

**pipaux.** The most important PIP package for the design. Spend the most time here.
Answer explicitly, in prose, in `notes/pipaux.md`:

* Is a whole series table loaded and then subset, or are specific cells requested?
* Is auxiliary data versioned, and at what level: file, series, or cell?
* When a single CPI value is revised, does any existing mechanism record which surveys
  used it?
* What does an auxiliary data update actually do, and is it idempotent?
* What would the natural partition key be, if each series were stored as partitions?

**pipdata.** Map the control flow of `pd_process_data()`: the loop unit, what is per
survey versus batch, and where auxiliary data enters. Then document
`dlw_validation_engine()` in detail: where rules live, their format, how country and
survey specific overrides are expressed, and what happens when a rule fails. Populate
`rules.csv` thoroughly; that table is the reason this package is being read. Also
document `pd_deflation()` and `pd_aux_attr()`: exactly which auxiliary values enter a
deflated welfare value.

**wbpip.** First question: is it actually pure? Any file read, path construction, option
read, or environment access is a finding and belongs in `io_points.csv`. Then input
assumptions: what does each entry point require of its input, and what happens when those
assumptions are violated. Keep the microdata path and the grouped data path distinct.

**pipapi.** Do not document the API surface. Document only the **input contract**: which
artifacts it requires, with what schema and primary keys, and what it assumes about their
freshness and internal consistency. This becomes the consumer side of the data contracts.

## 9. Consolidation

At the end:

1. Write `HARVEST.md`: date, commit SHA per package, what ran, row counts per table,
   which packages were skipped or done lightly.
2. Write `notes/CROSS_PACKAGE.md` covering:
   * **Contradictions.** Anything written but never read, read but never written, or
     where two packages disagree about a column name, type, or key.
   * **Undeclared dependencies.** Edges in `deps_internal.csv` absent from the
     `DESCRIPTION` files.
   * **Path construction outside `pipload`.** Any package building storage paths itself.
   * **Rules outside the rules engine.** Cleaning or validation logic hardcoded in a
     function rather than expressed as data.
   * **The auxiliary granularity answer**, restated in one paragraph, because it drives
     the entire incremental design.
   * **The `stamp` fit summary.** How many requirements came back `supported`, `partial`,
     `absent`, and `unknown`, and which `absent` ones block the pipeline.
   * **Overlap between `stamp` and `pipload`.** Both store and version artifacts. State
     plainly where they duplicate each other and where they differ.

## 10. What good output looks like

* `io_points.csv` has enough rows that the storage layout could be reconstructed from it
  alone.
* `aux_access.csv` answers without ambiguity whether auxiliary consumption is cell level
  or table level.
* `rules.csv` for `pipdata` is long, and the split between `defined_in = code` and
  `defined_in = data` is visible at a glance.
* `stamp_fit.csv` has rows marked `absent`. A table where everything is `supported` means
  the requirements were read off the README rather than tested against the source.
* `notes/stamp.md` answers all five questions with file and line evidence, and says
  plainly which ones could not be settled from the code.
* Every `notes/<package>.md` has a Gaps section with real entries.
* Nothing anywhere reads like a README.
